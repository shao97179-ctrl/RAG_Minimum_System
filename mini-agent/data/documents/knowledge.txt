# RAG 检索增强生成

RAG（Retrieval-Augmented Generation，检索增强生成）是一种将信息检索与大语言模型结合的技术架构。

RAG 的核心思想是：在 LLM 生成回答之前，先从外部知识库中检索相关信息，然后将检索到的内容作为上下文提供给 LLM，从而让 LLM 的回答基于事实而非仅靠参数记忆。

RAG 的工作流程如下：
1. 用户提出问题
2. 将问题转换为向量（Embedding）
3. 在向量数据库中检索最相关的文档片段
4. 将检索到的文档作为上下文，连同问题一起发送给 LLM
5. LLM 基于上下文生成回答

RAG 的优势：
- 不需要重新训练模型就能让 LLM 获取新知识
- 回答可以基于具体的文档内容，减少幻觉
- 知识库可以随时更新，灵活性强
- 适用于企业内部知识问答、技术文档查询等场景

RAG 的局限性：
- 检索质量直接影响回答质量，如果检索不到相关文档，回答可能不准确
- 需要维护向量数据库和知识库文档
- 对于复杂推理问题，单纯检索可能不够

# ChromaDB 向量数据库

ChromaDB（简称 Chroma）是一个开源的向量数据库，专为 AI 应用设计。

ChromaDB 的特点：
- 轻量级、易上手，适合快速原型开发和小规模应用
- 支持本地持久化存储，也支持内存模式
- 提供 Python 和 JavaScript SDK
- 内置 Embedding 函数支持（可自动调用 Embedding 模型）
- 支持 CRUD 操作：添加、查询、更新、删除文档
- 支持元数据过滤查询
- 完全开源，社区活跃

ChromaDB 的适用场景：
- 开发和测试阶段的小规模向量检索
- 嵌入式应用，不需要独立部署数据库服务
- 学习向量数据库和 RAG 的入门选择
- 数据量在百万级以下的应用

ChromaDB 的局限性：
- 不支持分布式部署，单机运行
- 大规模数据（千万级以上）性能不如专业向量数据库
- 缺少高可用、备份恢复等企业级特性
- 查询性能在海量数据时可能下降

# Milvus 向量数据库

Milvus 是一个高性能、分布式的向量数据库，由 Zilliz 公司开发并开源。

Milvus 的特点：
- 云原生架构，支持分布式部署和水平扩展
- 支持十亿级向量数据的高效检索
- 提供多种索引类型：IVF、HNSW、ANNOY 等，可按需选择
- 支持 GPU 加速，提升索引构建和查询速度
- 提供丰富的 SDK：Python、Java、Go、Node.js 等
- 支持混合查询：向量相似度 + 标量过滤
- 提供 Milvus Lite（嵌入式版本）、Milvus Standalone 和 Milvus Distributed 三种部署模式
- 支持多语言 Embedding 模型
- 完善的监控和运维工具

Milvus 的适用场景：
- 大规模生产环境的向量检索（千万到十亿级）
- 需要高可用和水平扩展的企业应用
- 推荐系统、图像检索、自然语言检索等
- 对查询延迟有严格要求的应用

Milvus 的局限性：
- 部署和运维相对复杂（分布式模式下）
- 对小规模应用来说过于重量级
- 学习曲线比 ChromaDB 陡峭
- 需要额外的基础设施（如 etcd、MinIO 等）

# ChromaDB 与 Milvus 的对比

ChromaDB 和 Milvus 都是向量数据库，但定位和适用场景有明显差异：

1. 定位不同：
   - ChromaDB 定位为"开发者友好的轻量级向量数据库"，适合快速开发和测试
   - Milvus 定位为"生产级分布式向量数据库"，适合大规模企业应用

2. 部署方式：
   - ChromaDB 是嵌入式数据库，直接在应用进程中运行，无需独立部署
   - Milvus 支持独立部署和分布式部署，需要额外的服务组件

3. 数据规模：
   - ChromaDB 适合万级到百万级数据
   - Milvus 适合百万级到十亿级数据

4. 扩展性：
   - ChromaDB 不支持分布式，无法水平扩展
   - Milvus 支持分布式，可以水平扩展

5. 易用性：
   - ChromaDB 更容易上手，几行代码即可使用
   - Milvus 配置更复杂，但提供更强大的功能

6. 索引类型：
   - ChromaDB 默认使用 HNSW 索引
   - Milvus 支持多种索引类型（IVF、HNSW、ANNOY、DiskANN 等），可按场景选择

7. 企业级特性：
   - ChromaDB 缺少高可用、备份恢复、监控等企业级特性
   - Milvus 提供完整的企业级特性支持

选择建议：
- 如果你是初学者或在开发测试阶段，选择 ChromaDB
- 如果你需要处理大规模数据或部署生产环境，选择 Milvus
- 如果项目从原型到生产，可以先用 ChromaDB 开发，再迁移到 Milvus

# Agent 智能体

Agent（智能体）是 AI 应用的一种架构模式，指 LLM 能够自主决定行动方式来完成任务。

Agent 的核心特征：
- 自主决策：LLM 根据用户输入判断需要采取什么行动
- 工具使用：Agent 可以调用外部工具（API、数据库、计算器等）
- 迭代执行：Agent 可以多步执行，每步的结果影响下一步的决策
- 目标导向：所有行动都是为了完成用户的任务

Agent 的工作模式：
1. 用户提出任务
2. LLM 分析任务，判断是否需要使用工具
3. 如果需要工具，LLM 选择合适的工具并生成调用参数
4. Agent 执行工具调用，获取结果
5. 将工具结果返回给 LLM
6. LLM 基于结果生成最终回答，或决定继续调用其他工具

Agent 与普通 LLM 对话的区别：
- 普通 LLM 对话：用户问 → LLM 答（只能基于训练知识回答）
- Agent：用户问 → LLM 判断 → 调用工具 → 获取实时信息 → LLM 基于真实数据回答

Agent 的典型应用：
- 客服机器人：调用订单系统、库存系统
- 研究助手：调用搜索引擎、论文数据库
- 编程助手：调用代码执行环境、文件系统
- 数据分析助手：调用数据库、计算工具、绘图工具

# Function Calling 函数调用

Function Calling（函数调用）是 LLM 的一种能力，让模型能够输出结构化的工具调用请求，而不是纯文本。

Function Calling 的工作原理：
1. 开发者定义一组工具（函数），包括名称、描述、参数 Schema
2. 将工具定义随消息一起发送给 LLM
3. LLM 根据用户问题判断是否需要调用工具
4. 如果需要，LLM 输出结构化的 tool_call（工具名称 + 参数 JSON）
5. 开发者在代码中执行对应的函数
6. 将函数结果返回给 LLM
7. LLM 基于结果生成最终回答

Function Calling 与 Prompt 方式调用工具的区别：
- Prompt 方式：在提示词中描述工具，让 LLM 输出文本格式的调用指令，需要自己解析文本
- Function Calling：LLM 原生支持，输出标准 JSON 格式，解析可靠，不易出错

Function Calling 的关键概念：
- Tool Schema：工具的结构化描述，包括名称、描述、参数类型
- Tool Choice：控制 LLM 是否必须调用工具（auto/none/指定工具）
- Tool Call：LLM 返回的工具调用请求
- Tool Message：工具执行结果的消息

Function Calling 的最佳实践：
- 工具描述要清晰，让 LLM 能准确判断何时使用
- 参数 Schema 要精确，类型和描述都要准确
- 不要暴露内部实现细节给 LLM（如 API Key、数据库路径等）
- 处理好工具调用失败的情况
- 控制工具数量，太多会让 LLM 难以选择

# Tool Calling 工具调用

Tool Calling 是 Function Calling 的更通用说法，在很多框架和文档中这两个术语可以互换使用。

Tool Calling 的本质是让 LLM 具备"使用工具"的能力，从而突破 LLM 本身的限制：
- LLM 不能做精确数学计算 → 通过 Calculator 工具
- LLM 不能获取实时信息 → 通过 Weather API 工具
- LLM 不了解特定领域知识 → 通过 RAG 工具检索知识库

Tool Calling 的核心组件：
1. 工具定义（Tool Schema）：告诉 LLM 有哪些工具可用
2. 工具调度（Tool Dispatcher）：根据 LLM 返回的 tool_call 找到并执行对应函数
3. 工具执行（Tool Execution）：实际调用 Python 函数
4. 结果回传（Result Return）：将执行结果返回给 LLM

一个完整的 Tool Calling 流程示例：
用户：北京天气怎么样？
  ↓
LLM 判断：需要调用 get_weather 工具
  ↓
LLM 输出：tool_call(name="get_weather", arguments={"city": "北京"})
  ↓
Tool Dispatcher：找到 get_weather 函数，执行 get_weather(city="北京")
  ↓
工具执行：调用 OpenWeather API，获取天气数据
  ↓
结果回传：将天气信息返回给 LLM
  ↓
LLM 基于天气数据，生成自然语言回答

# 向量数据库概述

向量数据库是专门用于存储和检索向量（Embedding）的数据库系统。

为什么需要向量数据库：
- LLM 和 Embedding 模型将文本转换为高维向量（如 768 维、1536 维）
- 语义相近的文本在向量空间中距离更近
- 向量数据库可以高效地在海量向量中找到最相似的 K 个（KNN 搜索）
- 这是 RAG 技术的核心基础设施

常见的向量数据库：
- ChromaDB：轻量级，适合开发测试
- Milvus：高性能分布式，适合生产环境
- Qdrant：Rust 实现，性能好
- Weaviate：支持混合搜索（向量 + 关键词）
- Pinecone：全托管云服务
- FAISS：Facebook 开源的向量检索库（非数据库）

向量数据库的核心操作：
- 插入：将文档的 Embedding 向量存入数据库
- 查询：给定查询向量，返回最相似的 K 个文档
- 删除：从数据库中移除指定文档
- 更新：修改已有文档的向量或元数据
